§1 Framework Overview — Duck Creek ManuScript Primitives

Before the domain sections it is worth naming the runtime primitives that appear throughout — this document quotes them directly from the code and expects the reader to recognise them.

ManuScript root

Every .xml under Billing/ManuScripts/** opens with <properties manuscriptID="…" inherited="…" versionDate="…">. The inherited= attribute is the single authoritative parent link. inherited="" means the manuscript is a root.

Confirmed roots: Billing_InvoiceData_1_0_0_0, Billing_Scheduling_DateCalculator_1_0_0_0, Billing_Schedule_Override_Data_1_0_0_0, Billing_EmailInvoiceData_1_0_0_0, Billing_Debit_Change_Notice_1_0_0_0, Billing_ClaimsAccountInvoiceData_1_0_0_0, DCT_AutomatedProcess_Base, DCT_AutomatedProcess_AsyncRetry.

Field kinds

  • <public …> — externally addressable field; usually bound to an XPath (path="@…" or path="…") into the session document.
  • <private …> — internal-only computed field; the <value> block is the calculation.
  • <request verb="…"> — dispatches a verb-based request (e.g. BillInvoice.getInvoiceDataAsXMLRq, Session.setLeafRq, StoredProc.callStoredProcRq).
  • <iterator …> (Request.loopRq in usage) — bounded loop; iteration count is a <nameValue name="iterations" …>.
  • <lookup> + <table id="…" tableType="local"> — inline lookup table with <rowKeys> and <data> rows; tableType="local" means the table is defined in the manuscript itself.
  • <affects><reference idref="…" effect="preEffect|postEffect|setValue"/></affects> — ordered side-effects that fire relative to the field's own evaluation.

Comparison operators

<comparison compare="eq|ne|gt|lt|le|and|or|is"> with <operand> children. Literals: <operand type="string" value="…"/> or <operand type="int" value="…"/>.

Date math

<dateAdd subtract="1"><dateArgument .../><dateUnit … unit="days"/></dateAdd> — subtract="1" flips add → subtract.

Return-code pattern

A <table id="…ReturnCode" tableType="local"> enumerates named keys, and <lookup><tableRef …/><fieldRef value="ReturnCode"/><keyRef … name="Status"/></lookup> writes a status back onto the response.

Carrier override pattern override

Each base rule set has a companion CarrierRules_<Feature> object with two boolean switches:

  • CarrierRules_<Feature>.OverrideBaseRules — if True, carrier rules replace base entirely.
  • CarrierRules_<Feature>.AddAdditionalRules — if True, carrier rules run in addition to base (gated on data.ErrorCode ≤ 0).
Both switches default to False in the base manuscripts (Billing_Frequency_Calculator_1_0_0_0, Billing_InstallmentAmounts_Calculator_1_0_0_0) — no live carrier override active for the amount split.

4.B Scheduling Algorithm (Frequency Calculator)

  1. Start-date resolution (IntialDateSet.StartDate spelling Intial retained) — earlier of PolicyTerm.PolicyTermEffectiveDate (or BillItem.ItemEffectiveDate for mid-term items) and the processing date.
  2. Target-due-day clamping — if DaysInMonth < TargetDueDay, use DaysInMonth; else use TargetDueDay.
  3. Days-prior-to-due (invoice lead time) — BuildInputParameters.DaysPriorToDue: EFT → EFTDrawOffsetDays; otherwise → PaperAndElectronicInvoice, which resolves to ElectronicInvoiceOffsetDays when AccountConfig_Invoice.ElectronicInvoice is on, or BillProductionOffsetDays otherwise.
  4. Agency / Collections exemption — when Account.AccountTypeCode equals AGT or COL2, DaysPriorToDue is forced to 0: no lead-time offset and no blackout-date shift.
  5. Installment date = DueDate − DaysPriorToDue.
  6. Loop control (Build.BuildData) — Request.loopRq with iterations = MaxNumberInstallments (+1 buffer); each iteration checks InstallmentCountPlusOne ≤ MaxNumberInstallments AND NextDateSet.DueDate ≤ EndDate.
  7. Two parallel builders in the same manuscript: Policy-Term-level (Build.*, IntialDateSet.*) for full-term/renewal, Bill-Item-level (BillItemBuild.*) for endorsement/misc/reinstatement mid-term items.

4.C Recalculation Logic

  • Triggers — ENDT, REIN, and Misc Credit/Debit (BillItem.MiscTypeCode ≠ "") all set Build.EvaluateExecuteEndorsementFirstInstallment, which sets Build.EndorsementSetMaxDate = DateTime.MaxValue and re-triggers Build.ExecutePolicyTermResultsBuild.
  • Stale-installment cleanup — BuildGetNextInstallmentDateSet.RemoveDateSets issues Session.removeElementRq purging Installments nodes where InstallmentDate ≤ NextInstallmentDate AND InstallmentDate > BillItem.ItemExpirationDate.
  • Missed / late-entered handling — _BillingWorkingDoc.IsMissedInstallment is True when the bill item's effective date is after its first unfiltered due date AND the transaction date is after the last scheduled installment date.
  • Late-entered strategy field — AccountConfig_Scheduling.LateEnterStgy / PolicyTermConfig_Scheduling.LateEnterStgy referenced, but branching logic per strategy code is Not Found in Codebase (search: Billing/ManuScripts/Billing/Billing/Scheduling/*.xml).
  • Bill-Item-level rebuild — BillItemBuild.EvaluateExecuteEndorsementFirstInstallment mirrors the pattern via BillItemBuild.EndorsementSetMaxDate.

4.D Short-Term Policy Logic

Confirmed absent from the Frequency / InstallmentAmounts manuscripts. No ShortTerm / STP field, code path, or table is present.
  • The ISTP charge type (Installment Setup Fee, fixed $10) is not a short-term-policy fee — it is the multi-installment-plan surcharge, confirmed in Carrier_Billing_Events_PolicyTerm_Post_Actions_1_0_0_0.xml (<nameValue value="10" name="Amount"/> + <nameValue value="ISTP" name="ChargeTypeCode"/>), gated by CarrierRules_PrevBilledFeeChargeEvent_WorkingFields.CheckConditionOtherThanAnnual = False — only non-Annual plans incur it.
  • Short-duration policies are handled emergently by the generic date-window algorithm (EndDate = PolicyTermExpirationDate − LastAvailDueDtDisp) combined with MaxNumberInstallments. There is no dedicated short-term rule set.

9.C Async / Batch Retry

  • Billing/BatchScripts/BatchRetryRequest.xml — scheduled batch that queries CustomServer.listSemaphoresRq for async requests where ResponseStatus = failure AND QueueStatus = 4.
